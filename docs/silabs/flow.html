SiLabs ↔ dstack: the actual packets on-chain

What really crossed the wire in the interop example — every line below is a real Base Sepolia transaction.

First, the thing to get right: neither node bootstrapped a key for the other. Each shows up with its own hardware-attested key — the SiLabs chip with its factory SE key (P-256, sealed in the die), the dstack CVM with its Phala-KMS-derived key (secp256k1). Registration publishes each node's attested identity; it doesn't share a secret. Sharing a secret is a separate, later step (4–6).

Both nodes are now members, each holding its own independent key. No secret has been shared. What the registry now knows: each public key is proven to live inside a specific TEE running specific, measured code.
4 · SiLabs shares a secret → dstack
onboard(→ dstack, ciphertext)
the secret is ECIES-encrypted to dstack's attested public key (read from the registry) and posted to dstack's inbox.
from 0x4af324d3… · to 0x63ca2560…
ciphertext 0x047a7d4d… (148 bytes, ECIES to 039e9a4f…)

↳ stored in _onboarding[dstack] · event OnboardingPosted
5 · ← dstack reads its inbox
getOnboarding() → ciphertext
the dstack CVM pulls the message and decrypts it with its private key — the one attestation proved is inside the enclave.
decrypt(privkey) → "shared-session-key:silabs↔dstack:…" ✓
How they shared it: the secret was encrypted to a key that attestation proved lives inside the dstack TEE running known code. So the SiLabs side (or an operator) can hand a secret to "the dstack enclave running app 0x915c8197…" and only that enclave can read it — no server, no shared KMS, no trust in the operator. Direction note: the reverse (→ SiLabs) needs ECIES inside the SE, since the chip's private key never leaves the die.
