A Pixel 6a that proves which code it runs — on-chain

Live attestation from a real Titan M2, verified in your browser against a contract on Base Sepolia.

The hardware: a Pixel 6a (bluejay) with an on-board Titan M2 secure element. Our unit — serial 27081JEGR17677, running GrapheneOS — signed the attestation below. Photo: Nisiguti, Wikimedia Commons, CC BY-SA 4.0.

This is a Pixel 6a (bluejay) running GrapheneOS, with a Google Titan M2 secure element on board. At boot the Titan M2 measures the system image and signs that measurement under a hardware key that chains to a root Google publishes — so anyone can check it, no vendor portal.

We baked our APK com.edgetee.attest into the read-only system partition (/system/priv-app/), re-signed the AVB vbmeta with our own RSA-4096 key, and re-locked the bootloader. The Titan M2 measures that vbmeta digest before Android starts, and via dm-verity it transitively covers the whole system partition — including our APK. So the verifiedBootHash the chip signs is a measurement of the exact code: change one byte of the APK → different system hashtree → different vbmeta → different digest → off the allow-list. This is the MRENCLAVE-style "measure the image" trust model, on a phone. Standard Key Attestation only binds the app's signer; here the code identity is the image digest itself.

Five certs, leaf-first. The leaf carries the hardware attestation extension and the per-key P-256 public key; it is signed by the Titan M2 batch attestation key, which chains up to Key Attestation CA1 — a root Google publishes in roots.json and that the verifier contract pins. Verified offline, byte-for-byte, against Google's published roots.

Titan M2 hashes the vbmeta image before Android starts and emits that digest as verifiedBootHash. vbmeta embeds the dm-verity hashtree descriptor whose root covers every block of the read-only system partition — including our baked-in APK. There is no path to change the APK without changing the system hashtree, the vbmeta, and therefore the digest the chip signs.

The code-signing key is removed from the trust model. Standard Key Attestation binds the app's signer (MRSIGNER); here the signer is gone. We re-signed vbmeta with our own AVB key only as the mechanism to make the system hashtree cover our APK — but the contract never reads who signed, and the green/yellow boot-state color is just a label for that. What it checks is deviceLocked and that the verifiedBootHash — the measurement of the exact image — is on the allow-list. That is MRENCLAVE: measure the code, trust no signer. Change one byte of the APK → different system hashtree → different vbmeta → different digest → off the list.

What this proves

proven The attestation was signed by a genuine Titan M2 whose batch key chains to a Google-published root; the chain verifies; deviceLocked=true; and the verifiedBootHash the chip signed equals the vbmeta digest that — via dm-verity — measures the exact system partition holding our APK.

measure the image Code identity here is the image digest, not the signer. Modify the APK and you get a different system hashtree, a different vbmeta, and a different verifiedBootHash — which is no longer on the allow-list, so the contract rejects it. This is the property standard Key Attestation could not give.

Trust model: you trust Google as the silicon root (the cert chain) and the owner's allow-list of image digests (allowedBootHashes). You do not trust the operator, a cloud, or any server — the check runs in a public contract. Honest caveat: the allow-list pins exact image digests, so a legitimate OS or APK update produces a new digest that the owner must add to the list — an MRENCLAVE-style versioned rollout, not an automatic one.

The system-partition baking, AVB re-signing, and verifier live alongside the captured attestation token and 5-cert chain — all from real silicon. The AVB key is a mechanism, not a trust anchor: the contract pins the measurement, not the signer.
