An STM32 that proves which code it runs — with an anchor its vendor never published

Live attestation from a real STM32H573 under ST's closed Secure Manager, verified in your browser against a contract on Base Sepolia.

This is an STM32H573I-DK running STM32Trustee Secure Manager — ST's closed secure firmware, at PSA isolation level 3. The initial-attestation key lives inside it. You hold the application signing key but are locked out of the secure domain entirely: you can boot code, but you cannot forge its measurement.

At boot, ST's immutable SMuRoT stage measures your non-secure application and Secure Manager signs a PSA attestation token (IETF EAT, COSE_Sign1 / ES256) carrying that SHA-256 as the NSPE software component. So the token says: “I am this specific ST die, and this is the hash of the application I booted.”

The catch — and how it was closed

Silicon Labs publishes its device root openly. ST does not. UM3254 Rev 8 §11.1.1 says the initial-attestation CA certificate is “delivered under license and must be requested from STMicroelectronics.” Buying the (free) Secure Manager package does not include it — its Utilities/Certificates/ ships exactly one PEM, the user root. Without an anchor, a verifier can check the chain's internal consistency and still have nothing to root it in.

The anchor was determined instead of obtained. A P-256 signature plus its message pins the signer to two candidates. One die gives two candidates that both “work” by construction — circular. Intersecting two independent leaves leaves exactly one key:

Both halves are externally reproducible: the user manual is a free download, and the silicon is purchasable. The intersection self-validates — one wrong byte changes the digest, changes the recovered candidates, and the sets go disjoint. Positive control: the same machinery run against the DUA user leaf recovers ST's published user root exactly.

ST has already published enough to determine its own gated anchor. Two independent leaves are what pin the key — and ST has printed two: Figure 7 of UM3254 (die …014b28) and Figure 60 of the Secure Manager wiki page (die …10111c). Those are different dies, both in public documentation, and together they are sufficient. No silicon is needed in principle.

We used our own die as the second sample only for a mechanical reason: the wiki figure is a 658×458 raster, too coarse to transcribe its base64 byte-exactly (it parses with the right issuer and the stated 470-byte length, but r comes out off-curve). Nothing is being kept secret here — an anchor delivered “under license” is recoverable from the vendor's own manuals, and licensing a public key was never going to keep it private.

The STM32 chain is only depth 2 — the leaf is signed directly by a self-signed CA — so the entire path to the root fits in two RIP-7212 calls. The verifier does both: one proves the IAK was certified by ST, the other proves the token came from that IAK. No off-chain chain walk is trusted. (The SiLabs adapter, at depth 4, has to pin a fingerprint and delegate the walk off-chain; this is the variant its own docs describe as future work.)

The measurement really follows the code

Not an assertion — a demonstration. Adding host-nonce support changed the application, and the attested measurement moved with it:

old app
0effd5249cc2e3d1…4b070f
new app
92a7e9ee73c8465e…485e071

The verifier rejected the stale value. And the new one is reproducible offline from build output alone — SHA256(header ‖ app.bin ‖ zero-pad ‖ protected_tlvs), the region MCUboot signs — which independently agrees with the image's own IMAGE_TLV_SHA256. So a third party can compute what should be attested and compare it with what was.

Three vendors, one registry — and it is any-to-any

The H573 shares a TEEBridge with a Silicon Labs SiMG301 and a Phala dstack TDX confidential VM: two edge microcontrollers from different silicon vendors, and a datacenter enclave, each proven by its own verifier module.

loading members…

onboard(fromMemberId, toMemberId, payload) takes any two members — nothing is wired pairwise. Verification factors per vendor, not per pair: N platforms need N modules, not N² bridges, because every module reduces its vendor's native evidence to the same (codeId, pubkey, userData) triple. Three is how many parts have had hardware bring-up, not a limit of the design.

What this proves — and what it doesn't

proven An ST-held key, inside firmware the operator cannot enter, signed a fresh token carrying the SHA-256 of the operator's own application; the whole chain to a pinned anchor verifies inside a public contract; the device is a live registry member.

anchor is determined ST hands out a signed CA certificate; we hold a public key pinned by intersection. That is all a verifier needs, and it is reproducible from public material — but it is not the same artifact as a published root, and whether it may be relied on commercially is a question for counsel.

Trust model: you trust STMicroelectronics as the silicon manufacturer. You do not trust the operator, a cloud, or any server — the check runs in a public contract.
