How it works
Verifier sends a nonce
A random challenge prevents replay. The phone receives it via POST /attest over an ADB-forwarded Unix socket.
Phone computes its own APK SHA-256
The AttestService reads its own APK file from getApplicationInfo().sourceDir and hashes it. No signing key involved.
Derives a bound challenge
cert_challenge = SHA-256(nonce_utf8 ‖ apk_hash_bytes). This links the fresh nonce to the specific APK hash claim inside the hardware-signed certificate.
Titan M2 generates and signs an attestation cert
Android KeyStore asks the StrongBox to create an ephemeral P-256 key. The StrongBox issues a cert including attestationChallenge, verifiedBootHash, deviceLocked, and the caller's package identity. The key is immediately deleted.
Verifier checks five properties
(1) cert chain roots at Google's attestation CA · (2) attestationSecurityLevel = StrongBox · (3) deviceLocked = true + verifiedBootState ∈ {Verified, SelfSigned} · (4) verifiedBootHash matches the pinned GrapheneOS build · (5) attestationChallenge = SHA-256(nonce ‖ claimed_apk_hash). All five pass → the prover is a specific locked Pixel 6a running the specific APK it claims.
Security properties
Hardware root Google attestation CA → Titan M2 (StrongBox), separate secure element
Code identity granularity APK SHA-256 self-reported by running code; OS-granularity (verifiedBootHash) independently hardware-measured. On a locked AVB device, dm-verity protects system partitions so the self-report is trustworthy if APK is in the system image.
Signing key in trust path? No. Verifier pins verifiedBootHash (OS) + APK hash (via challenge). Signing key appears only in softwareEnforced and is not checked.
Freshness Verifier-supplied nonce bound into cert challenge; key deleted after each request
Physical attack resistance Titan M2 is a discrete secure element (PSA / FIPS boundary). verifiedBootHash provided to Titan M2 by bootloader before Android starts — OS cannot tamper with it.
